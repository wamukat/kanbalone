# リリース手順

GitHub Actionsでリリースを準備・公開します。どちらのワークフローも`main`から実行します。タグのpushだけでは公開されません。

## チームの運用ルール

### ブランチとマージ

- `main`を常にリリース可能に保ちます。長期の`develop`ブランチや常設のreleaseブランチは作りません。
- 作業は最新の`main`から短命の`codex/<ticket>-<topic>`ブランチを作り、1つの目的に絞ったPRにします。ドキュメント・CI修正も同じです。
- マージには **Required checks** の成功と、利用者によるチャット上の受け入れ確認が必要です。GitHub上の承認件数は必須にせず、エージェントがレビュー指摘・CI結果・受け入れ対象の差分を確認してマージ操作を行います。受け入れ後に内容が変わった場合は、その変更を説明して再確認します。AIレビューだけで受け入れ済みとは扱いません。最新のmainを取り込み、原則squash mergeし、マージ後に作業ブランチを削除します。
- 管理者の保護ルール回避は通常作業では使いません。障害復旧などで必要な場合は、リポジトリ責任者が理由・確認結果・追跡PRを記録します。チャットでの受け入れ確認を省略したり、通常の直pushを代替手段にしたりしません。
- リリース準備にはActionsが作る`codex/release-VERSION`を使います。準備開始から対象SHA確定までは無関係なPRのmainへのマージを待ち、対象の変更を固定します。SHA確定後は通常開発を再開できます。
- 緊急修正もmainから短命ブランチ→PR→patchリリースで進めます。mainに公開できない変更がある場合は先に整理し、古いタグからの独立した保守版公開は別途方針を決めます。現在のCIはmainに含まれるSHAのみ公開できます。

### 誰が、いつ確認するか

| タイミング | 担当 | 実施・記録する内容 |
| --- | --- | --- |
| 実装PRを出す前 | 実装者 | ローカルで変更に応じたテストと実操作を確認。PRに手順・結果・制約を記録。UI変更は日英の対象画面、既存画面との統一感、変更前後の画像を確認する。 |
| 実装PRのマージ前 | 利用者が受け入れ、エージェントが確認・操作 | 差分・CI結果・実操作の記録を確認。UIの見た目や操作感はE2E成功だけで受け入れない。 |
| リリース準備PR | リリース責任者＋レビュー担当 | 前回公開版から対象版までの差分を確認し、バージョン・日英ノート・移行ガイドを完成させる。マージ後の完全なSHAを記録する。 |
| dry-run成功後・公開前 | リリース責任者 | 候補イメージartifactをローカルの隔離環境で起動し、主な変更と基本操作を確認。対象SHA、dry-runのURL、候補artifactのID、イメージID、確認結果を準備PRに追記し、そのartifactの公開可否を決める。 |
| 公開後 | リリース責任者 | 公開されたタグ・日英ノート・イメージを確認し、公開版を隔離環境で起動してバージョンと基本操作を確認。Release URLを準備PRへ追記する。 |

実装時の確認は、公開前の候補版確認の代わりにはなりません。公開前のローカル確認には、下記の検証付きロード手順でdry-run artifactの`image.tar`を読み込み、`loaded-image.json`の`localImageId`を指定して起動します。専用のポート・volumeを使い、既存の稼働環境へ上書きしません。

DB・保存形式・更新手順に影響する変更では、公開前に旧公開版で用意した検証データをバックアップし、候補版への更新・内容照合・バックアップからの復元を確認します。UIやAPIだけの変更では、その非該当理由を記録します。実ユーザーデータを使う場合は整合性の取れたコピーのみとし、画像やログに個人情報を含めません。

公開にはローカルで確認したdry-run artifactのイメージをそのまま使います。バージョンやSHAが変わった場合はdry-runをやり直します。別のartifactを使う場合は、ローカル確認と公開承認を取り直します。公開後はバージョンタグから取得したイメージが検証済みのイメージと一致することを確認します。

### リリースノートと公開判断

- 実装PRで「利用者にとって何が変わるか」と互換性・移行への影響を記載します。最終ノートはリリース準備PRの`docs/releases/vVERSION.md`で日英とも完成させ、マージ前にレビューします。公開後に初めて書く運用にはしません。
- ノートは変更内容、破壊的変更、移行手順、既知の制約を簡潔に記載します。該当しない項目はその旨を明記します。公開時にはこのファイルが使われます。
- リリース責任者が対象範囲とバージョンを決めます。v1以降は互換性のある修正をpatch、機能追加をminor、非互換変更をmajorとします。v1未満も非互換変更は明記します。
- 通常は正式版のバージョンで準備を始めます。dry-runで正式版候補をビルド・検証し、ローカルの隔離環境で確認してから、そのartifactのIDを指定して同じイメージを公開します。公開前のワークフロー検証はdry-runで行います。
- RCを公開するのは、正式版の前に利用者に先行版を配布し、一定期間試用してもらう必要がある場合に限ります。その後の正式版ではバージョンと対象SHAが変わるため、正式版用の準備PR、dry-run、ローカル確認を行います。
- レビュー、dry-run、ローカル確認、公開承認が揃ったら、リリース責任者が承認済みの候補artifactのIDを指定して`publish=true`を実行します。タグは公開ワークフローが作成します。
- 現在のCIはローカル確認の記録や人の公開判断を自動では検証しません。責任者が準備PRの記録を確認して実行します。GitHubのワークフロー実行承認と、製品の公開判断は別のものです。
- 稼働中のローカル環境やユーザー環境の更新は、公開とは別作業です。更新依頼を受けてからバックアップ・更新・確認を行います。

## リポジトリの設定

初回リリース前に、管理者が次を確認します。

- `main`のルールでPR経由とCIの **Required checks** を必須にし、GitHub上の必須承認件数は0件にする。チャットでの受け入れ確認は運用で守る。
- ActionsからのPR作成と、以下のワークフローで使用する権限を許可する。
- このリポジトリからGHCRへ公開でき、利用者が認証なしでイメージを取得できる。
- 必要に応じて、contents／pull requestsのwrite権限を持つGitHub Appをインストールし、リポジトリ変数`RELEASE_APP_ID`とシークレット`RELEASE_APP_PRIVATE_KEY`を設定する。

App未設定の場合、Prepare releaseは`GITHUB_TOKEN`を使用します。準備PRのワークフロー実行が承認待ちになったら承認してください。Appのトークンを使うと、この追加の実行承認を省けます。[GitHub公式のトークン仕様](https://docs.github.com/en/actions/concepts/security/github_token)

ワークフローを追加しただけでは、ブランチ保護・パッケージ公開範囲・Appは設定されません。別途確認してください。

## 1. リリース準備PRを作る

1. **Actions → Prepare release → Run workflow**で`main`を選び、`v`なしのバージョンを入力します。通常は`1.2.0`のような正式版を指定し、先行試用を行う場合は`1.2.0-rc.1`のように指定します。
2. `codex/release-VERSION`ブランチとPRが作成されます。`package.json`、OpenAPI、現在のインストール例、`docs/releases/vVERSION.md`が更新されます。
3. 日英のリリースノートを完成させます。利用者にとっての変更点、破壊的API変更、移行手順、既知の制約を記載し、必要なら移行ガイドをリンクします。両言語のレビュー後にプレースホルダーと`RELEASE_NOTES_DRAFT`マーカーを削除します。
4. 差分をレビューし、**Required checks**の成功を確認してマージします。レビュー済みのリリース内容を含む`main`の完全な40文字のコミットSHAを控えます。

準備ブランチが既にある場合は、上書きせず既存PRを更新します。ブランチ作成後にPR作成だけ失敗した場合は、設定や権限を修正して、その既存ブランチからPRを作成します。過去の移行例やエビデンスのバージョンは変更しません。

## 2. 公開せずに検証する

**Actions → Release → Run workflow**で`main`を選び、次を入力します。

| 入力 | 値 |
| --- | --- |
| `version` | レビュー済みバージョン。`v`なし |
| `sha` | `main`に含まれる完全な40文字の小文字コミットSHA |
| `publish` | `false` |
| `candidate_artifact_id` | 空欄 |

対象SHA・バージョン・リリースノートを検証し、共通チェックとChromium E2Eを実行します。続いて`linux/amd64`イメージをビルドし、隔離した一時volumeで起動・API書き込み・再起動後の永続化を確認します。

実行が成功したら`release-image-VERSION-attempt-N` artifactをダウンロードします。実行概要またはartifact URLの`/artifacts/ID`部分から数値IDを控え、dry-runのURLとともに記録します。artifactには検証済みイメージと、コミットSHA、イメージID、アーカイブのチェックサムを含む`manifest.json`が入っています。dry-runではタグ・GitHub Release・GHCRイメージを公開しません。

イメージの保存前に、v0.9.35・v0.10.0・v0.11.0からの更新とバックアップ復元を検証専用データで確認します。`upgrade-restore-RUN_ATTEMPT` artifactも確認し、候補版のローカル確認と、必要に応じて利用者固有の構成の確認を行ってください。[更新検証の手順](../migration-guide.md#automated-upgrade-verification)を参照してください。

### ローカルへ成果物を読み込む

取得した`image.tar`と`manifest.json`を同じディレクトリに置き、レビュー済みのバージョン・完全なSHAを指定します。

```bash
RELEASE_VERSION=1.2.0 RELEASE_SHA=レビュー済みの40文字SHA \
  node scripts/load-release-image.mjs release-artifact
```

この手順はarchiveのチェックサム、対象版・SHA、保存されたmanifestとconfigのdigestの関係、読み込み後のレイヤー構成を照合します。成功時に`loaded-image.json`を作成します。そこに記録された`localImageId`で、専用のポート・volumeを使って起動してください。

Dockerの保存方式によってCIの`imageId`とローカルのIDが異なる場合があります。実地確認ではCIのmanifest digestに対し、ローカルではconfig digestが使われました。IDを推測したり、ラベルが一致するだけの別イメージを使ったりせず、この検証で対応を確定してください。元の`manifest.json`は書き換えず、両方のIDを準備PRに記録します。対象は単一のLinux/amd64イメージです。イメージストアの違いは[Docker公式資料](https://docs.docker.com/engine/storage/containerd/)も参照してください。

## 3. 公開する

リリース責任者がローカルの検証結果と、そのartifactの公開承認を確認したら、**Actions → Release → Run workflow**で`main`を選びます。

| 入力 | 値 |
| --- | --- |
| `version` | dry-runと同じバージョン |
| `sha` | dry-runと同じ完全なコミットSHA |
| `publish` | `true` |
| `candidate_artifact_id` | ローカルで確認したartifactの数値ID |

公開実行は、artifactがこのリポジトリの`main`から起動した`Release`の成功済みdry-runに由来することを確認します。ダウンロード結果、manifest、アーカイブ、イメージを検証し、指定したバージョン・SHAとの一致を確認します。そのイメージを使い、ビルド、共通チェック、Chromium E2E、更新・復元テストは繰り返しません。旧ワークフローのartifactを使っていた場合は、新しいdry-runから始めます。

バージョンタグと下書きGitHub Releaseを作成し、`vVERSION`／`VERSION`タグでイメージをpushします。認証なしでpullし、検証済みイメージの実体・ラベルとの一致を確認してから、日英ノートと検証記録を公開します。現在のlatestより新しい安定版のみ`latest`を更新し、RCなどのプレリリースでは更新しません。

公開後はリリースノート、バージョンタグ、認証なしのイメージ取得を確認します。公開イメージを隔離環境で起動し、結果を準備PRに記録します。チェックログ、テストレポート、リリース成果物のartifact保存期間は30日です。公開記録には元の実行とartifactの情報、およびローカルDockerイメージIDとは別のregistry digestが含まれます。

## 失敗時の対応

- 出所や整合性の検証に失敗した場合は公開を停止します。記録したバージョン、SHA、artifactのIDを照合してください。期限切れ、削除済み、または条件を満たさないartifactの場合、そのバージョンのGitタグ、GitHub Release、レジストリのタグがまだ存在しないときに限り、dry-runからやり直してローカル確認と公開承認を取り直します。公開実行ではartifactの差し替えや再ビルドは行いません。
- 公開実行は、注釈付きGitタグの作成時に候補artifactのIDとチェックサムを記録します。途中で失敗した場合は、失敗ジョブを再実行するか、同じバージョン、SHA、artifactのIDで公開を再実行します。dry-runの再実行で別のartifactが作られても元のIDを使います。
- 旧ワークフローで作成したタグのように候補の記録がない場合や、既存タグ、Release、イメージが候補と一致しない場合は公開を停止します。タグや下書きReleaseの作成、イメージのpushがすでに行われ、元のartifactを取得できない場合は、公開を止めて調査します。復旧できなければ、既存のタグ・Release・イメージを維持し、新しいバージョンを準備します。
- 公開済み版の不具合は新しいpatch版で修正します。ユーザーDBのロールバックや稼働中コンテナの更新は、このワークフローでは行いません。

## CIの検証範囲

`ci.yml`は全PRと`main`へのpushで動作し、パスによる除外はありません。`verify.yml`でfrozen install、`pnpm check`、Chromium E2Eを実行します。CIではDockerのビルドとスモークテストも実施し、前提ジョブの失敗・中断・skipを **Required checks** の失敗として扱います。

ソースアーカイブには利用者向けの`skills/kanbalone-api`だけを許可し、`dev/skills`などの開発用スキルの混入を検出します。Dockerにはスキルを含めません。`pages.yml`によるドキュメントサイトの公開は、製品リリースとは独立しています。

[CIの実装状況と導入時の確認事項](./release-ci-plan.md)も参照してください。
