# レーンによる完了判定への移行案

この文書はv0.10.0で導入した仕様と移行方針の記録です。下記の互換APIはv0.10.0〜v0.11.0時点の内容であり、次回リリースでは削除します。現行の置き換え先・エラー仕様は[非推奨APIの削除と移行手順](../migration-guide.md#deprecated-api-removal)を参照してください。

## 目的と合意事項

レーンとチケットの完了フラグによる二重管理を解消する。
レーンに完了扱いの属性を設け、チケットの完了状態を所属レーンから決定する。
完了レーンへの移動で完了、通常レーンへの移動で再開となる。
複数の完了レーンを許可し、名前による判定は行わない。
チケット単体の完了チェックは廃止する。

アーカイブは独立して残す。アーカイブ・復元でレーンを移動したり、完了状態を上書きしたりしない。
レーン属性の変更はアーカイブ済みを含む所属チケット全体に作用するため、変更前に対象件数と影響を示す。

Group の active 判定は、この完了判定を利用する。
Group は所属0件、または未完了かつ未アーカイブの所属チケットが1件以上あれば active とする。
親子の完了状態を連動させる仕様は追加しない。

## v0.10.0導入時の影響範囲

| 対象 | 現状 | 必要な変更 |
| --- | --- | --- |
| DB | `tickets.is_resolved` が判定元。`lanes` は名称・順序のみ | レーン属性を判定元にする。古いフラグは検索用の派生値としてDBトリガーで維持し、独立した判定元にはしない |
| 読み取り | mappers・検索・関連チケットが個別フラグを参照 | 詳細・一覧・親子・関連・blocker・フィルターを一貫した判定に揃える |
| 作成・更新 | `isResolved` / `isCompleted` を指定可能 | レーンの値から決定し、矛盾する指定は拒否する |
| 移動 | transition、position、move、一括操作が別経路 | 全経路で移動先レーンの完了状態を反映する |
| レーン操作 | 作成と名称変更のみ | 完了属性の作成・変更と全体への通知を追加する |
| UI | 編集チェック、詳細からの再開、一括完了がある | レーン選択による移動へ統一。再開先を暗黙に選ばない |
| 表示 | 完了・アーカイブをまとめて折りたたむ | 新判定で動作を確認し、独立したアーカイブの意味を明示する |
| export/import | レーン名とチケットフラグを復元 | レーン属性を保存し、旧形式の不一致を明示的に処理する |
| 外部連携 | import は選択レーンを使う。refresh は外部状態を保持し、ローカル完了を変更しない | ローカル完了はレーン、外部状態は参照情報という分離を維持する |
| 利用者向け契約 | OpenAPI、日英ガイド、ヘルパー、配布スキルに完了フラグの例がある | 読み取り互換・書き込み変更・移行手順をまとめて更新する |

## API互換の提案

- レーン属性名は `isCompletionLane` とする。通常の追加レーンは false。
- 標準テンプレートの done レーンは作成時に明示的に true とする。利用者指定の名前からは推測しない。
- 読み取りの `isResolved` と互換名 `isCompleted` は維持し、レーン由来の同じ値を返す。
- 検索の `resolved` / `completed` も互換を保つ。
- 作成・更新・transition で旧フラグが指定された場合、操作後の所属レーンと一致する値だけ許可する互換動作を維持する。
- 矛盾する旧フラグは状態を変えずに 409 を返し、移動先レーンの指定を案内する。両方の旧フラグが異なる場合も黙って片方を採用しない。
- 一括完了は一括レーン移動に置き換える。複数ある完了レーンから自動選択しない。旧一括完了APIはdeprecatedとし、一致する状態の確認だけ許可する。不一致は409。
- レーンの完了属性変更はトランザクションとボード更新通知で反映する。UIにはアーカイブ済みを含む対象件数を表示する。一覧からの保存では確認時の全レーン属性・件数を期待値として渡し、確認後に変わった場合は無変更で再確認を求める。

## 既存データの移行（合意済み）

既存の完了フラグを正として保持する。レーン名・多数決・コメントの解釈では完了を判断しない。

1. 既存レーンには完了属性 false を設定する。Doneや完了という名前でも、名前・順序・意味を変更しない。
2. 完了済みチケットがあるボードごとに、専用の完了レーン `Completed (migration)` を末尾に新規作成する。同名があれば `Completed (migration) 2` などの連番で重複を避ける。既存レーンは流用しない。
3. 完了済みチケットだけを新規レーンへ移す。未完了チケットのレーンは維持する。
4. アーカイブ済みの完了チケットも移動対象とする。完了・アーカイブ状態、チケットID、親子関係、コメント、外部参照を維持する。
5. 新規レーン内はアーカイブ状態、元レーン順、元チケット順、IDの順で安定配置する。移動元の残りの相対順を保持して位置を詰める。
6. 移動前のレーンID・位置と移動先をチケット履歴に記録する。
7. 完了チケットがないボードには新規レーンを作らない。空のDoneも通常レーンのままにする。
8. スキーマ変更・移動・履歴を1トランザクションで適用し、失敗時は全体をロールバックする。属性の存在を移行済みの印として、再起動時に再作成しない。

旧exportの取り込みも、完了属性のないレーンに属する完了チケットを専用レーンへ移す。
新形式のexportは完了属性をそのまま復元し、矛盾するチケットの旧フラグは全体ロールバックで拒否する。

この方式により、Done内の未完了チケットをアップグレードのために個別判定する必要はない。
人間の受入判断は移行後の通常運用として行う。個別調査で作った完了候補を自動適用しない。

適用前に整合性の取れたDBバックアップを保存し、コピーで全チケットの完了・アーカイブ・親子・所属を照合する。
旧バージョンは新スキーマの契約に対応しないため、ロールバックはコンテナイメージだけでなく切替前DBを復元する。

### 受入待ちの扱い

既存運用では「Doneに移すが、人間の確認まで未完了」という使い分けがある。
受入待ちレーンの名称は `Acceptance` とする（2026-11-21合意）。
通常レーンの `Acceptance` と完了属性を持つ `Done` に分け、AIの作業・検証終了はAcceptance、人間が受け入れてDoneへ移す運用を想定する。
名称は運用例であり、完了判定は名前ではなくレーン属性による。
この運用変更をKanbaloneのガイド・配布スキルにも反映する。A2O側の変更は今回の対象外とし、別途検討する。
既存の受入待ちチケットは、実装完了・AIによる受入レビュー・リリース検証の記録だけで人間の最終受入済みとみなさない。
既存データは上記のフラグ保持移行に従う。Doneというレーン名だけで人間の受入済みとは判断しない。

## 検証範囲

- 通常／完了レーンへの作成、単体・一括・D&D・position・ボード間移動。
- レーン属性変更の詳細・一覧・関連チケット・検索への反映。
- 完了レーン0件・複数件、レーン名変更、空レーン削除。
- 完了状態とアーカイブの4通り、およびアーカイブ後のレーン属性変更。
- 旧フラグ一致／不一致／別名間の矛盾、不正入力時に全件無変更。
- export/import の往復、旧形式の混在データ、移行の再実行・失敗時ロールバック。
- 外部Issueの状態がローカルのレーン・完了状態を上書きしないこと。
- 画面の完了チェック撤去、レーン属性設定の影響確認、移動による完了・再開。

## 実装順

1. 完了フラグを保持する移行とAPI互換方針に沿って実装する。
2. DB・読み取り・全更新経路・移行を隔離データで実装、検証する。
3. UI・OpenAPI・日英ガイド・使用例・スキルを揃える。
4. 全体チェック・E2E・既存DBコピーでの確認後にローカル実行環境へ反映する。
5. この変更を土台としてGroupの残りの仕様を確定し、実装する。

## 採用したUI

歯車領域内をボード名・完了レーン・データ操作・削除に分ける。完了レーンは現在値と変更ボタンを表示し、変更時だけチェック一覧を展開する。選択は下書きであり、既存チケットへの影響確認後に一括保存する。名前変更はレーン上のインライン編集を維持する。初回UI作成後の案内は非モーダルで、ブラウザ・ボードごとに一度表示する。

`PUT /api/boards/:boardId/completion-lanes` で全選択を1トランザクションで保存する。全レーンのID・完了属性・アーカイブ込み件数を期待値として渡し、不一致時は409で無変更とする。
