# Group 仕様

状態: 利用者向け仕様とUI方針は合意済み。DB・API・UIと関連ドキュメントへ実装を反映し、動作・整合性の確認段階。リリース済みという意味ではない。
前提: v0.10.0で完了状態は所属レーンから決まる。アーカイブは完了とは独立している。

## 目的

一定の目的で取り組むチケット群をまとめ、未完了の作業がなくなれば通常の一覧から自然に外れるようにする。
タグとは別の用途を持たせ、チケットの階層を増やすことは今回の目的に含めない。

## 合意済みのルール

| 項目 | 仕様 |
| --- | --- |
| 名前 | Group |
| 範囲 | ボード内限定。複数ボードをまたがない |
| ボード間移動 | 移動するチケットのGroup所属を解除し、残るチケットは元のGroupを保持する |
| 項目 | 名前と任意のMarkdown説明。名前だけで作成でき、説明は後から追加・編集できる |
| 所属数 | チケットは最大1つのGroupに所属する。未所属も許可する。複数所属はタグとの使い分けが曖昧になるため採用しない |
| 別Groupへの付け替え | 初版は「解除→追加」。Groupへの追加検索は未所属のみを対象とし、直接の付け替え操作は提供しない |
| 親子チケット | 親子でつながるチケット全体が同じGroupに所属する。所属変更はアーカイブ済みを含む親子でつながるチケット全体に反映する |
| 所属済みと未所属の親子化 | 保存時に所属済み側のGroupへ自動で揃える。未所属側の既存の親子チケットも含めて所属変更し、追加確認は表示しない |
| 分離 | 親子関係を解除しても、それぞれ元のGroupを保持する |
| 異なるGroup間の親子化 | 「Aに揃える」「Bに揃える」「キャンセル」を選ぶ。所属変更と親子化を一体で適用する |
| Group間の関係 | 関連・親子・階層を持たない |
| 終了・アーカイブ | Group自身に終了状態やアーカイブ操作を持たせない |
| active | 所属チケットが0件、または未完了かつ未アーカイブの所属チケットが1件以上ある場合 |
| inactive | 所属チケットが1件以上あり、未完了かつ未アーカイブのチケットが0件の場合 |
| 一覧 | 通常はactiveのみ表示・返却する。フィルターでinactiveも取り出せる |
| 過去の所属 | inactiveになっても所属を保持し、Group指定でチケットを取り出せる |
| 削除 | 所属チケット0件のGroupだけ削除可能。チケットの連鎖削除はしない |
| Undo | Group単独では導入しない。導入する場合は他の操作も含めて共通仕様を検討する |

active判定は各チケットを対象とする。親だけ完了しても、未完了・未アーカイブの子があればactiveのまま。
未完了チケットの復元や通常レーンへの移動でも判定に従ってactiveに戻る。
最後の所属チケットが外れると0件になるためactiveになる。不要なら明示的に削除する。
Groupの所属変更では、チケットのレーン・完了・アーカイブ状態を変更しない。

## 合意したUIの方向性

- Kanban / List / Groupで表示を切り替える。既存サイドバーは維持する。
- コンテンツエリア内にGroup一覧を置き、その右側に選択したGroupの内容を表示する。
- Group一覧末尾の「＋」から、その場で名前を入力して作成する。
- Group名の下に説明を表示する。空の場合は「説明を追加」。Markdown編集・プレビュー・保存・キャンセルを提供し、長文は折りたたむ。
- 既存チケットの追加は、親子関係の追加UIと同様にタイトル・番号で検索して選択する。子を選んでも親子チケット単位で追加する。検索候補は未所属のみ。
- 解除ボタンは常時表示。親子がある場合は親のみ、単独チケットにも表示する。
- 単独・親子チケットとも解除前に確認する。親子チケットの確認にはアーカイブ済みを含む全件を示す。
- アーカイブ済みチケットは通常隠し、一覧末尾の開閉で元の親子構造を保って表示する。
- 親だけアーカイブ済みで表示対象の子がある場合、親は関係表示として残す。この親にも親子チケットの所属解除ボタンは置く。
- 完了済み・未アーカイブのチケットは通常表示する。GroupのActive / Allとアーカイブ表示切り替えは独立する。

## Groupの削除確認（合意済み）

アーカイブ済みを含む所属チケットが0件の場合のみ削除できる。
既存の削除操作と同様に、Group名と「この操作は取り消せません」を示し、「キャンセル／削除」で確認する。

## 実装したAPI・データ設計

詳細な契約は [Group 技術設計](group-technical-design.md) を参照。

- API: Group CRUD、active/all/inactive一覧、Group指定のチケット取得、親子チケット単位の所属変更。アーカイブ済みも含む取得は `archived=all` を明示する。
- 競合: 所属変更previewとcommitのexpectedToken、Group編集のexpectedRevision、削除のIf-Matchで古い確認を検出する。親子編集は編集開始時のeditTokenと追加対象の親も照合する。
- 原子性: 所属変更・親子編集・作成・ボード移動をtransactionで処理する。異なるGroupの親子化は候補から所属先を選び、本文等と一括保存する。
- 移行: 既存チケットは全件未所属で開始する。JSON formatVersion:2にGroup定義と所属を保存し、旧形式は未所属として取り込む。SQLiteバックアップにもGroupを含める。
- 履歴: 所属変更は各チケットの活動履歴へ記録する。Group作成・改名・説明変更・削除は専用のGroup履歴と取得APIへ記録する。
- 外部連携: GitHubからの新規取り込みは未所属、同期ではローカルのGroup所属を保持する。
- 日英ドキュメント、OpenAPI、AI向けガイド、API使用例、配布スキル、migration guideへ契約を反映する。

## UI用語

新たな概念名として「家族」は使わない。親子関係は「親子チケット」と表現する。操作ボタンは「3件まとめて外す」「2件まとめて追加」のように件数と動作を示し、確認本文で親子チケットが対象であることを説明する。

### 親子化でのGroup確認（最新の合意）

所属済みと未所属の親子化では、通常の保存時に所属済み側へ自動で揃える。既存の親子チケット・アーカイブ済みを含む対象全体に反映し、追加の確認画面は表示しない。同じGroup同士・両方未所属の場合もGroupに関する追加確認は不要。

異なるGroupに所属するチケット同士を親子化する場合だけ、「Aに揃える」「Bに揃える」「キャンセル」を表示する。親子関係と所属変更は一体で適用する。

これは親子化時のGroup確認に関するルールであり、Groupから明示的に外す操作の確認は引き続き行う。

### Group画面からの新規作成

Group画面では、未所属の既存チケットの追加に加えて、現在のGroupに所属したチケットを新規作成できる。レーンなどは既存のチケット作成と同様に指定する。チケット追加の「＋」から「既存チケットを追加」「チケットを新規作成」を選択し、タイトル・本文・レーン・優先度を入力して作成できる。作成フォームは既存のUIを再利用する。

### チケット詳細からGroupへの移動

チケット詳細に所属Group名をリンクとして表示する。クリックで詳細を閉じ、Group表示に切り替えて対象Groupを選択する。inactiveの場合はAll表示に切り替えて一覧にも対象を表示する。未所属はリンクのない「未所属」表示。所属の追加・解除はGroup画面に集約し、詳細には説明全文や所属編集を追加しない。

### 並び順（合意済み）

Group一覧は「作成順（昇順）」「作成順（降順）」「名前順（昇順）」「名前順（降順）」の4種類から選択できる。Group内のチケットは既存Listと同等の並び順とする。

初期値は作成順（昇順）。並び順の選択はボードごとに、既存の表示設定と同様の方法で保持する。

### Group名の編集（合意済み）

Group名はGroup画面で直接編集できる。同一ボード内の同名Groupは許可しない。inactiveも重複判定の対象。前後空白除去・NFC正規化後の完全一致で判定し、大小文字・全半角は同一視しない。名前は1〜100文字（Unicodeコードポイント数）。
説明は既存チケットと同じMarkdown表示・安全対策を再利用する。上限は100,000文字（Unicodeコードポイント数）。

### Group画面の検索・フィルター（合意済み）

初版では、所属チケット一覧の検索・タグなどによるフィルターは提供しない。既存画面の検索・フィルター状態もGroup画面には適用しない。
Group一覧のActive / Allと並び順、アーカイブ済みチケットの表示切り替えは提供する。
既存チケットをGroupに追加するための検索は引き続き提供する。

### 異なるGroupの親子化の確認UI（合意済み）

「どちらのGroupに揃えますか？」として、変更後の親子構造と現在の所属Groupを表示する。双方のGroup名を明示した選択ボタンに、所属が変更されるチケット番号を併記する。アーカイブ済みの既存の子も対象に含める。選択と同時に親子関係・所属変更をまとめて保存し、追加の確認は重ねない。キャンセルでは未保存の編集に戻る。

## 技術設計とレビュー

[Group 技術設計](group-technical-design.md) にAPI・DB・競合・移行の実装契約、2名のサブエージェントによる設計レビュー履歴と実装後の修正内容を記載した。3Group以上の衝突、明示ソート時の親子表示、新規作成と親指定を同時に行う場合の扱いは、調査で見つかった追加論点として同書に記載し、以下の方針で合意済み。


### 追加論点の合意

1. 3種類以上のGroupの衝突でも、候補Groupの数だけ選択肢を表示する。
2. Group内はソート時も親子構造を維持する。Listと共通の比較ルールを親同士・子同士へ適用する。
3. 新規作成と親指定を同時に行う場合も、通常の親子化と同じ所属ルールを適用し、異なるGroupだけ確認する。作成結果の所属先が開始時のGroupと異なる場合は、その所属先を開く。
