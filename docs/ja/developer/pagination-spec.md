# チケット一覧のページング仕様（#1509 / #1510）

2026-11-22。ユーザ合意: GUI全般を対象、並び順はparameter指定。既存互換、limit/cursor、途中更新時再取得、nextCursor＋total、条件適用後の平坦なページ、閲覧状態維持。

## 1. 対象と互換性

`GET /api/boards/:boardId/tickets` に任意のページングを追加する。limit/cursor/orderのない既存呼び出しは件数、既定順、レスポンス構造とも変更しない。既存の全フィルタをそのまま利用できる。

GUIのチケット一覧取得全般（Kanban、List、Group、詳細の候補選択、ボード設定、完了設定）を対象とする。ボード一覧・Group一覧・コメント・監査履歴のページングはこのチケット一覧APIの対象外。

## 2. 入力と応答

- `limit`: 1〜200の整数。初回ページでは必須。継続も必須とし、前ページと異なる件数を許す（5→50）。
- `cursor`: サーバが返した不透明な文字列。初回は省略。条件を変更したらcursorを外して再取得。公開offset/page番号は提供しない。
- `order`: `id_asc`、`position_asc`、`completed_desc`。ページング時の既定は`id_asc`。`position_asc`は従来順（lane_id ASC, is_archived ASC, position ASC, id ASC）、`completed_desc`は現行完了レーン順（完了日時 DESC, position ASC, id DESC）。完了日時NULL/不正値は現行UI同様に最古扱い。limitなしのorder指定は全件を指定順で返す（レスポンスにpageを付けない）。
- 不正なlimit/order/cursor、limitなしのcursor、別ボード・条件・順序へのcursor流用は400。limitはcursorの条件に含めない。条件の正規化でパラメータ順・省略時の既定値差を吸収する。
- ページング時だけ従来のticketsに`page: { nextCursor: string | null, total: number }`を追加。hasMoreは追加しない。最後はnextCursor=null、空結果はtickets=[]/total=0/nextCursor=null。totalはフィルタ後の全体件数である。
- `priority`: 任意の優先度集合（例`priority=1,3`、1〜4のカンマ区切りOR）。重複・順序を正規化し、省略は全優先度。不正値は400。既存GUIの優先度条件をLIMIT前に適用し、表示件数/totalの食い違いを防ぐ。
- ticket要素の既存フィールド・意味は変更しない。

```http
GET /api/boards/4/tickets?lane_id=45&order=completed_desc&limit=5
GET /api/boards/4/tickets?lane_id=45&order=completed_desc&limit=50&cursor=<nextCursor>
```

## 3. 変更中の整合性

永続的なボード単位の一覧revisionをDBで管理する。ticketの追加・変更・削除・移動、レーン/完了設定、タグ/Group情報、親子/依存/関連、remote/external参照など、一覧の内容・条件・順序に影響する変更で更新する。移動は元と先の両ボード。見落としを避けるため同じボードの表示用データ変更を保守的に無効化してよい。無関係な別ボードの更新では無効化しない。ボードをまたぐ依存/関連で返却情報が変わる場合は、参照する側のボードも無効化する。

cursorはboard/filter/order/revision/最後のソートキーに紐付ける。古いrevisionは409 `{error: "ticket list changed; restart pagination"}`。同じ応答のtotal、rows、revisionは同一read transactionで取得する。ページング応答の`X-Kanbalone-Ticket-Revision`ヘッダで同じrevisionを返し、GUIが並列取得したレーン別集合の版を比較できるようにする。JSONのpage構造は増やさない。版が異なる集合は混ぜず、ボード単位で最大2回取り直す。カーソルで変更前のsnapshotを保持しない。サーバ再起動後も変化がなければ継続できる設計を優先する。cursorを改変して任意SQLや任意キーを実行できないよう検証する。

複数ページを集める利用者は409で部分結果を破棄し最初から取得し直す。書き込みを伴うAI処理は、一覧を収集し終えてから変更するか、処理済みIDを管理して再実行を安全にする。永遠に自動再試行しない。

## 4. GUI全般への適用

共通のページ取得/集約ローダーを使い、limitなしのチケット一覧呼び出しをGUIに残さない。ボード切替・条件変更・古い非同期応答で別の画面へ結果を混ぜない。409時は部分結果を破棄して最大2回再試行し、続く場合は既存のエラー表示で再操作可能にする。

- List、Groupの親子一覧、選択候補、設定の全体判定は、200件ずつ集めて完全な集合から現行の並び順・親子表示・件数・一括操作を計算する。部分集合を全件と偽らない。初版でList/Groupに新しい「もっと見る」や親子分断を導入しない。
- 完了レーンはレーンごとにcompleted_descで初期5件、押下で50件追加。totalに全体件数を表示。未完了レーンは共通ページローダーで取得する。未取得の完了チケットを選択肢・親子・依存の判定に必要とする操作は別途完全取得/詳細取得を行う。
- 通常のUIでは最後の完了状態を解除すると「未完了＋完了」に戻る従来動作を維持する。内部状態が空になった場合の防御処理ではチケット取得を省略し空結果とする（全件を取得して誤ったtotalを表示しない）。
- 検索・各フィルタはすべてサーバへ渡してからページを区切る。GUIの補助表示用フィルタが残る場合も未取得分を0件と解釈しない。
- 再取得でも展開済み件数を維持する。ボード/検索条件が変わった場合は初期化する。更新でチケットが消えた場合を除き閲覧位置を保つ。完了への移動直後は先頭の新しい完了チケットが見える現行動作を維持する。
- 「もっと見る」の通信中は多重実行を防ぐ。失敗時は既存の行/スクロール/追加ボタンを保ち再試行できる。新しい恒常的な設定やページ番号UIは追加しない。

この範囲はGUI全般へのページングAPI適用であり、List/Group全体の遅延描画を完了したという意味ではない。大量の未完了カード描画や部分一致検索の走査コストは別の改善課題。

## 5. 実装・検証の条件

SQLでlimit＋1件とキー継続条件を適用し、そのページの関連情報だけ組み立てる。全件をJSへ読み込んでsliceする実装にはしない。totalはCOUNT、必要なindexを検討。配布物に依存を増やさず既存SQLite/Nodeを利用する。

互換API、limit境界、不正cursor、全order同順位、全フィルタ、空/終端、5→50、再起動、削除/移動/完了/関連変更による409、別ボードの非干渉、応答内整合をテスト。GUIでは全画面と候補取得、200件境界の親子/タグ/検索、一括操作、完了5→55→更新、失敗再試行、古い応答、詳細復帰、日英を確認。1,000/10,000件の再計測で効果と回帰を分けて記録する。
