# キーボードで仕事を続けるための改善状況

初稿: 2026-11-22（v1.0.0を調査した検討案）。更新: 2026-11-28、実装確認の基準はmain `92571d1e2fcef1a37d630fa02733e7f2c2ce0b83`。以下の「実装済み」はこのソースの状態であり、公開済みv1.6.0や利用中の環境にすべて含まれるという意味ではない。従来の候補キーと未実装の記述を、実際に採用した操作と残る評価に整理した。

## 狙い

**記録する、探す、確認する、次へ進む。そのたびに手を止めない。**

AIがAPIで作業を進める一方、人の確認だけが多くの画面移動やマウス操作を必要とすると、協働全体の流れが滞る。キーボード操作は「個人とAIが仕事を続ける場所」という[位置づけ](../product-positioning.md)を支える。

キーボードを好む開発者が作業を続けやすくすることと、実利用者の操作時間が短くなったことは区別する。現時点で比較できるのは実装・機械操作・保存と復帰の結果であり、実利用者の速度や習熟効果は未測定である。

## 現在の操作と適用範囲

| 操作 | 実装済みの挙動 | 範囲・制約 |
| --- | --- | --- |
| `/` | 検索欄にフォーカス | Kanban/List。Group・Groupなしでは、その表示にチケット検索がある場合に使える。別ビューへ暗黙に移らない |
| 検索欄の `↓` | 一覧のチケットタイトルへ移る | Kanban/List。Listは↑↓、Kanbanは↑↓でレーン内・←→でレーン間のフォーカス移動 |
| `Enter` / `Esc` | 詳細を開き、閉じると元のチケットと位置へ戻る。タイトル上のEscは検索へ戻る | 対象が絞り込みなどで消えたときは検索へ戻る。候補や未保存確認の既存操作を維持 |
| `N` | 既存の新規作成画面を開く | チケットなど対応する対象にフォーカスがあるとき。Kanbanのレーン、Groupの所属など既存作成文脈を引き継ぐ |
| `M` | フォーカス中の1票について同ボードのレーンを選ぶ | Kanban/Listのみ。一括選択とは独立。現在のレーンは確定不可。移動先選択→移動→取消のTab順 |
| `Ctrl+Enter` / `⌘+Enter` | 表示中・有効な確定操作を実行 | チケット保存、本文・Task・コメント、取り込み、共通移動・確認など。取り込みのPreviewやGroup競合の選択を省略しない |
| Group内のチケット検索 | タイトルや `#ID` の一致へ移動し、詳細を開く | 表示中のGroup/Groupなしの行が対象。画面外の仮想行も探せる。全ボード横断検索ではない |

操作の説明は[利用ガイド](../user-guide.md#キーボードで探して開く)、確定と取消の並び・安全な初期フォーカスは[ダイアログ方針](dialog-button-policy.md)にまとめる。新しい常設ボタン列は作らず、既存のツールチップとアクセシブルな説明で補う。専用のヘルプダイアログ、`?`、`j/k`、Ctrl/Cmd+K、汎用コマンドパレットは採用済み仕様ではない。

- Group検索と仮想化: [検索実装](../../../public/app-group-window-search.js)、[比較と制約](../../development/evidence/2026-11-23-virtual-group-kanban/README.md)。初稿の「Groupには検索を置かない」は現行仕様ではない。

これらは、日英の対象操作、保存後の取得、取消・失敗、フォーカス・スクロールなど、記録した条件の証拠である。機械テストのTab探索上限や固定待ち時間を、利用者の打鍵数・所要時間に読み替えない。実機のOSショートカット、IME、スクリーンリーダー、各ブラウザの全面検証とはしない。

## 維持する共通ルール

- フォーカス中の対象と一括選択を区別する。入力欄やIME変換中は通常の文字入力を横取りせず、リピートで重複送信しない。
- 保存・移動中は対象を固定する。失敗した移動と、保存に成功した後の画面再取得失敗を別の結果として伝える。
- キーによる確定も表示中の確認画面・API・入力検証を使う。削除確認は確定ボタンを先に配置してもCancelへ初期フォーカスを置く。
- Group競合は名前付き選択を維持し、非表示の共通Saveをキーで実行しない。閉じるだけの通知にも確定を追加しない。
- 文字キーの発見性と支援技術との共存は引き続き評価する。特に `/` はボード上の広い範囲で有効で、無効化・再割当UIはない。入力中の抑止だけを根拠に[WCAGの文字キー要件](https://www.w3.org/WAI/WCAG22/Understanding/character-key-shortcuts.html)への適合を宣言しない。

## 残る判断と評価

1. **反復操作の使い心地を測る。** 作成、検索→詳細→復帰、コメント→レーン移動を、同じ件数・順序・画面幅で評価する。初回学習と習熟後を分け、打鍵数、マウスへの持ち替え、時間、誤対象更新、入力消失を記録する。
2. **発見性を確認する。** 既存の説明だけでMやNへ到達できるか、今どの票を更新するかを利用者が説明できるか確認する。必要と分かった場合にだけヘルプの追加をモックで検討する。
3. **未対応範囲を決める。** GroupやカスタムビューへのM展開、全ボード検索、コマンドパレットは現行の対応範囲を広げる別判断であり、本書による実装承認ではない。
4. **実環境で検証する。** 実スクリーンリーダー、OS/ブラウザ差、日本語IME、200%拡大を確認する。未確認の組み合わせは未確認と記録する。

2026-11-22には新規作成と検索の優先、および共通検索の比較検討に合意した。その後は既存検索欄へのフォーカスと各ビューの検索を実装しており、独立した共通検索ダイアログを今から必須作業として再開しない。[改善状況と残件](improvement-roadmap.md)に沿って、現在の問題から優先順位を決める。

## 比較資料の位置づけ

[2026-11-22の実機比較](product-hands-on-comparison.md#5-キーボード操作から得たこと)ではKanboardの `n` とVikunjaの `Cmd+K` を操作した。これは当時の比較対象バージョンの観測であり、現在のKanbaloneと再比較した結果ではない。競合のキー配置をそのまま採用する根拠にも、実利用者の速度差の証拠にも使わない。
