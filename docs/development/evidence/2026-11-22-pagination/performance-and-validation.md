# ページング実装の性能と最終検証

[実装 PR](https://github.com/wamukat/kanbalone/pull/31)

## 対照を交互に測ったAPI結果

元の1,000件/10,000件fixture（未完了30%・完了70%）を別SQLiteへ整合コピー。Before=c4ea904、After=after-revision.jsonのソース指紋。両方Node26.13.1、localhost keepalive、3回ウォームアップ＋10回、取得順を交互に変更。本文受信・JSON解析・件数検証を含む。E2E/ブラウザ計測と同時実行していない。

|件数|操作|版|中央値 ms|最大 ms|応答 bytes|返却件数|
|---:|---|---|---:|---:|---:|---:|
|1,000|all|before|27.27|28.5|517,539|1,000|
|1,000|all|after|26.65|28.67|517,539|1,000|
|1,000|completion_initial|before|18.42|20.85|362,272|700|
|1,000|completion_initial|after|7.68|18.08|2,804|5|
|10,000|all|before|281.4|321.99|5,231,563|10,000|
|10,000|all|after|307.41|316.22|5,231,563|10,000|
|10,000|completion_initial|before|191.71|199.97|3,662,003|7,000|
|10,000|completion_initial|after|6.63|15.04|2,859|5|

`completion_initial`は、従来の完了レーン全件取得と、新しい初回5件取得の比較。返す件数は異なるが、画面にまず5件表示するための取得コストを比較している。10,000件で応答量は3,662,003→2,859 bytes。初回5件の中央値は191.71→6.63msとなった。画面全体の描画時間を測った値ではない。

引数なし全件取得は同一のSQL・応答量を保つ。10,000件の中央値は281.40→307.41ms、最大は321.99→316.22msであり、この小標本から完全な無劣化を保証しない。旧・新DBのEXPLAINではいずれもtickets_active_board_lane_position_idxを使用した。最初のページング設計時の計測とは計測時点/JSON解析の有無が違うので、その値を直結した前後比は使わない。

## 分割取得のコスト

別の候補版単独計測（3回ウォームアップ＋10回）で、全件を200件ずつ集約した結果。JSON解析・件数/重複検証を含む。

|件数|操作|中央値 ms|応答 bytes|リクエスト数|
|---:|---|---:|---:|---:|
|1,000|legacy_all|28.49|517,539|1|
|1,000|done_first5|3.55|2,804|1|
|1,000|done_next50|3.79|25,946|1|
|1,000|collect_all200|38.55|518,591|5|
|10,000|legacy_all|313.05|5,231,563|1|
|10,000|done_first5|12.4|2,859|1|
|10,000|done_next50|4.3|26,306|1|
|10,000|collect_all200|412.37|5,244,104|50|

10,000件をすべて集める場合は一括313.05msに対して50リクエストで412.37ms。List/Group/候補の完全性を維持する初版では、この往復とメタデータのコストがある。各レスポンスは200件以内になるが、総転送量や描画負荷が解消したとは主張しない。高遅延ネットワークではさらに不利になり得る。後続の遅延表示・検索最適化は別設計が必要。

## 最終チェック

- `check-final.txt`: pnpm10.33.0 / Node26.13.1でpnpm check成功。192テスト、OpenAPI、backend/public型チェック、ドキュメントbuild。
- `e2e-full.txt`: Chromium全147ケースの初回は145成功・2失敗。1件は全操作assertionとpage.close成功後のapp.close待ちtimeout。もう1件は実行開始後にテストの誤った仕様解釈を直して名前を変更したためのworker登録不一致。
- `e2e-rerun.txt`: 製品コードを変更せず、上記2件を現在のテスト定義で単独実行し2件成功。現在の147ケースは全て成功結果を確認したが、初回全件一発成功とは記載しない。
- `e2e-teardown-analysis.json`: 最初の終了待ちtimeoutのtrace要約。原因を製品不具合と断定していない。
- 追加の重点8ケースとレーン間移動中の整合性E2Eも個別成功。独立サブエージェントのcode/画像レビュー承認済み。
- `upgrade-data-check.json`: 元のv1.0.0 fixture DBを候補版で起動しても、既存17テーブルの全内容が一致。新テーブル/trigger/indexは追加のみ。production DBは更新していない。
- `ticket-attachments.json`: 比較画像12枚を実ブラウザで読込確認（1440×1000、naturalWidth/Height）。

ベンチマークの再実行には、同じfixtureを3592（候補）と3593（対照）で起動し、benchmark-api.py、benchmark-paired.pyを逐次実行する。プロセス/CPU/OSキャッシュのばらつきは残る。
