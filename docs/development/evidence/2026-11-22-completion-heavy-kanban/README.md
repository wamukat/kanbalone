# 完了チケットが多い Kanban の計測（#1512）

## 実行環境の区別

この初期計測は最新main（ページング導入済み）を対象にしている。通常のローカル環境3470はまだ公開版v1.0.0であり、その体感をこの計測と同一視しない。v1.0.0の同一データによる実機比較は[公開版との比較](release-comparison.md)を参照。公開版は完了5枚だけを表示するが、APIからは全件取得する。

## 結論

完了レーンの初期5件取得を後回しにする根拠は今回のローカル計測では得られなかった。100件の未完了に9,900件の完了を追加しても初期表示の差は約24 msだった。一方、新規作成／詳細を開くと毎回全件を取得し、約0.6秒かかる。こちらを別タスクで検討する。

起動時の同一ボード二重取得を除くブラウザ内の試作では約86 ms改善した。これは本実装ではなく、ルーティング全般の回帰検証前の診断結果である。

## 再現条件

- 実装基準: `1c87193ec553cbbd4bbc563f5a28b7ee67611600`。製品ファイルは変更していない。
- macOS 26.7.3 / Intel Core i7-9750H / Node 26.13.1 / Chromium 159.0.8154.6 / SQLite 3.54.1。
- 1440×1000、light、英語。ローカルHTTP、遅延注入なし。同時の重い検証なし。
- 独立DB3個、それぞれ1ボード。未完了100件（3レーンに34/33/33件）、完了0/900/9,900件（完了レーン）。本文500文字、タグ1個、親子／Group／アーカイブなし。
- 既存ユーザDBは使っていない。ポート3614/3615/3616。
- 各条件1回ウォームアップ後5回。条件順を往復させた。毎回新しいブラウザコンテキスト。中央値を記載。機器・データ依存の観測値であり一般的な保証ではない。
- `app-state.js` だけブラウザのroute overrideで状態オブジェクトへの観測参照を公開。状態／操作ロジックは不変。
- 初期表示はDOM件数、ready/loading/renderPending、8件のticket応答を確認して2フレーム後。最初のpaint/readyは一時的な状態を含み得るので、安定した初期表示としては扱わない。
- N/Enter計測は初期ロード完了後、実際のカード#1をフォーカスしてキーボード入力。keydownからdialog.openを観測した2フレーム後まで。新規作成はタイトルへのフォーカスとlane1、詳細はticket1を確認。保存操作は行っていない。

## 計測結果

| 完了件数（未完了は100件） | 初期表示 | N→新規作成 | Enter→詳細 | エディタを開く際の全件取得ページ数／本文bytes |
|---|---:|---:|---:|---:|
| 0 | 368.9 ms | 48.2 ms | 40.2 ms | 1 / 49,898 |
| 900 | 385.3 ms | 89.0 ms | 70.6 ms | 5 / 526,959 |
| 9,900 | 392.5 ms | 630.9 ms | 636.2 ms | 50 / 5,336,113 |

全サンプルで未完了100枚、完了min(件数,5)枚。初期取得は各レーン2回、計8件のticket API。初期ticketレスポンス本文の合計は100,100 / 105,854 / 105,904 bytes。bytesはPerformanceResourceTiming.encodedBodySizeでありHTTPヘッダ等を含む通信総量ではない。

| 完了件数 | 未完了レーン1/2/3 API応答時間中央値 | 完了レーン API応答時間中央値 |
|---|---:|---:|
| 0 | 4.6 / 6.1 / 7.8 ms | 8.5 ms |
| 900 | 4.0 / 5.8 / 8.6 ms | 9.7 ms |
| 9,900 | 3.9 / 5.6 / 8.4 ms | 9.8 ms |

各レーンの値は5回×二重取得の10応答。並列リクエストの待ち時間を含むブラウザ側の値でありSQL単体時間ではない。初期表示全体にはJS読込・DOM生成・描画も含む。EXPLAINでは完了上位5件が `tickets_paging_completed_idx`、件数がcovering indexを使う。毎回全件ソートしているわけではない。COUNTの件数依存コスト自体がゼロという意味ではない。

## 二重取得を除く診断試作

`startup-prototype.mjs` はブラウザの `app.js` 応答だけを書き換え、`main` の `refreshBoards` から最初のdetail取得を省く。ルーターによる取得は維持。サーバ／製品ファイルは不変。

9,900完了、各1回ウォームアップ＋5回交互実行:

| | 基準 | 試作 |
|---|---:|---:|
| 初期表示中央値 | 365.8 ms | 280.2 ms |
| ticket API件数 | 8 | 4 |
| 表示カード数 | 100+5 | 100+5 |

試作側の安定確認は4応答、基準側は8応答。URL `/boards/1` だけの評価であり、空ボード・root・List・Group・チケットdeep link・履歴移動等の正しさを証明しない。実装する場合はそれらの回帰検証が必要。

## 次の対応候補

1. 起動時の二重取得をなくす。取得順やルーティングを変えるため、上記各ルートを検証してから実装完了とする。
2. 新規／詳細エディタが必要とする親子・依存候補等を整理し、全件取得を待たず開く方式を別途検討。候補の欠落や古い関係での保存を避ける必要がある。
3. 完了レーンの遅延取得は今回は見送る。共通revision・ドラッグ中の再描画・古いレスポンスの混入等の複雑さに見合う改善は確認できなかった。

## ファイルと再実行

`revision.json` は基準・実行環境・入力DBと主要ソースのSHA256。`measurements.json` は54サンプル（ウォームアップを含む）、`startup-prototype.json` は12サンプル。`query-plan.json` はSQL計画。スクリーンショットは各条件の最終試行のboard/new/detailで、時間の証拠は画像ではなく計測JSONである。今回はbaseline調査のみであり、修正前後の画像比較ではない。日本語UI・親子等の機能回帰はこの負荷調査の対象外。

再実行は必ず基準 `1c87193ec553cbbd4bbc563f5a28b7ee67611600` の独立checkoutで行う。修正後のブランチでは初期8リクエストの待機条件が成立しない。このフォルダの `.mjs` をリポジトリルート下 `coverage/completion-heavy/` にコピーし、そこを作業用に使う。スクリプトはルートから実行する。

```sh
node --experimental-strip-types coverage/completion-heavy/seed.mjs
node --experimental-strip-types coverage/completion-heavy/server.mjs 0
# 別ターミナルで server.mjs 900 と server.mjs 9900 も起動
node coverage/completion-heavy/measure.mjs
node coverage/completion-heavy/startup-prototype.mjs
node --experimental-strip-types coverage/completion-heavy/query-plan.mjs
```

seedは既存DBがあれば停止する。比較入力を再利用する際に既存DBを上書きしない。既存アプリや他の検証との同時負荷を避ける。
