# Interface language

The UI supports English and Japanese. `public/app-i18n.js` chooses Japanese for a primary browser language of `ja` or `ja-*`, otherwise English. A valid explicit `kanbalone:language` browser preference overrides detection. If persistent storage is blocked, session storage is attempted; if both fail, the current language and page are retained with an error.

The sidebar settings language selector reloads the current route. Ticket drafts and visible inline editing forms require confirmation before reload. Cancelling retains the draft and the current language selection. Board data, API request fields, API values and API responses are not localized.

## Adding UI copy

- Use `t("English source", { name: value })` (or the `tr` alias) in renderers. Add the Japanese translation in `public/locales/ja-common.js`, `ja-board.js`, or `ja-editor.js`.
- Mark static HTML with `data-i18n`, `data-i18n-title`, `data-i18n-aria-label`, or `data-i18n-placeholder`. Initialization applies these before app rendering. Do not add a document-wide translation observer.
- Use named placeholders for complete messages. Escape values at HTML output boundaries; `t()` returns plain text and does not sanitize HTML.
- Never pass user titles, descriptions, comments, names or external event text through `t()`. Known application activity messages and known API error messages may be translated for display; unknown diagnostics remain verbatim.
- Keep shared translations identical. Catalog tests check missing explicit keys, interpolation parameters and duplicate-key consistency.
- Preserve API/provider identifiers, Markdown content, URLs and generated filenames. Japanese view labels do not change stored view-mode values.

Run the catalog/rendering tests, the locale E2E tests and public typecheck. Capture comparable English/Japanese screenshots, including narrow layouts, and follow the per-ticket image evidence rules. Existing English E2E tests continue to protect behavior and selectors.
