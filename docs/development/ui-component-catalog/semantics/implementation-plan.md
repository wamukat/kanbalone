# 共通部品を段階的に整える計画

既知の表示差を直しながら、既存のCSSと描画処理を共通定義として使う範囲を増やします。変更対象は、明確に再現できた是正、同じ役割で複数の利用先がある基本型、実際に起きた不整合を検知する回帰検証です。全4段階を終えた時点で、対象の利用先で定義が使われ、状態・操作・保存の契約が確認できることを完了条件にします。[方針の評価](architecture-assessment.md) · [基本型と用途差](design-consistency.md) · [初期6変更単位](shared-components.md)

## 範囲と基準

調査記録は基準SHA `2ff8489d889706a6dc6392fd28aeff073e0b515c` の21領域・1,301行、実測115フレームです。これは調査時の[PR #73](https://github.com/wamukat/kanbalone/pull/73)のheadで、カタログの作業ツリーもその上にあります。調査時点でPR #73は開いており、今回の実施計画への合意とPR #73の機能受け入れは別の判断です。通常の実装ブランチは受け入れ・マージ後の `main` から起こし、カスタムビューの順序selectを含む作業ではマージ済みの内容と調査時のツリーのうち対象の差分を照合します。変更があれば、関係する場面の基準を撮り直します。独立した修正の準備は現在の `main` でも可能で、先行する場合は同じ問題をその版で再現し、PR #73由来の変更が混ざらないことを確認します。[版と観測範囲](../evidence/README.md) · [リリース運用](https://github.com/wamukat/kanbalone/blob/2ff8489d889706a6dc6392fd28aeff073e0b515c/docs/en/developer/release.md#team-operating-rules)

今回の母集団は以下の作業単位に記載する利用先です。範囲を追加する場合は根拠と影響先を示し、別の変更単位で扱います。

- 画面全体や仮想化の行、選択方式、API・保存形式は維持します。役割を揃える対象は下地・既存レンダラー・明示した入力差です。
- ボードとビューのナビ密度、新規ボード入力の強調面、異なる用途を持つ検索や選択の統一は今回の実装対象から外します。
- 実測不足の4群は、コメントの外部送信、領域内の状態・エラー、移動先指定、Group所属変更の影響確認です。横断の統合は保留し、既存の経路を維持します。共通ルール変更が付随して及ぶ操作は回帰確認の対象です。[38群の観測と判定](style-comparison.md)

## 段階と依存

段階は実装と確認の優先順です。下記の依存を満たす準備・実装は並行でき、段階内の完了条件は関連作業を照合してから判定します。

| 段階 | 作業単位 | 段階の完了条件 |
| --- | --- | --- |
| 1. 既知の表示差を直す | P0、P1、P2、P3 | 基準と利用先を固定し、リモートのチェック、明暗の本文とリンク、初回案内を現行定義で表示できる。短い利用契約と利用箇所・検証が製品差分と同期する。 |
| 2. 同じ宣言を共有する | P4、P5、P6 | ボタン、入力、面とメタ情報の対象利用先が基礎定義を使う。同値整理では描画・周辺配置・操作が基準と揃い、変更する表示は別単位として説明される。 |
| 3. 同じ役割の見た目を揃える | P7 | 並び順selectとコメント本文欄に限定し、意図した文字の太さ・余白の差と、機能やフォーカスの維持を確認する。 |
| 4. 再発を検査し、利用先を確定する | P8、P9 | 未定義トークンの扱いと検査を決め、対象の利用先・例外・代表回帰・保留理由を確認する。固定版の記録と現行仕様から相互にたどれる。 |

### P0 基準・利用先・受け入れ条件を固定

- **依存** なし。実装ブランチを作る際は上記PRの依存を確認。
- **優先と範囲** 最初。既知の差と対象利用先、ソースの定義元、例外、確認する状態を次の作業単位に引き継ぐ。小さな現行契約は `docs/development/ui-component-contracts.md` に置き、`docs/development/ui-ux-review.md` から辿れるようにする。P0で雛形を用意し、P1の製品差分と検証に合わせて最初の契約を反映する。固定版の監査資料は根拠として参照する。監査の独立レビューは完了済みで、製品差分を `main` に取り込めるかはPR受け入れで判断する。
- **検証と完了** 採用する `main` のSHAと現在の観測の差分を照合し、同条件の再現手順と合成データを確認。旧観測を使う場合は版・状態が一致する根拠を残す。実装に入る前に利用先一覧と判定基準を共有する。P0の資料作成だけでは第1段階を完了しない。
- **推奨モデル・担当** Solが調査と資料、Astraが影響範囲を確認、進行担当が基準と受け入れを管理。

### P9 対象の利用先と回帰ガードを閉じる

- **依存** P1〜P8。照合表の準備・既存テストの選定は先行できる。
- **優先と範囲** 完了確認。まず定義元と実利用先の差分を照合し、P4〜P7の対象に残った重複・逸脱だけを対応する。ボタン・入力・選択・チェック・ダイアログ・文字・タグ・リンク等の基本型から、適用画面と許容差を現行仕様に記録。共有のタグや状態表示を使うKanban／List／Group／カスタムビューは、利用実績と既存の回帰を確認する。
- **検証と完了** 実際に発生した境界のうち、型の漏れ、ダークの前景、順序値や本文入力、状態の見分けを代表E2Eで検出できることを確認。対象利用先が共通元を消費し、例外・保留・未確認の状態には理由と再検討条件がある。固定のカタログ検査は基準値とリンクの整合として扱い、現行版の計測を個別に保存する。対象群に利用先がない定義、実装されていない契約、未解決の対象内ガードを残して完了扱いにしない。
- **推奨モデル・担当** Solが利用先・証拠・テストを照合、Astraが横断境界を独立レビュー、進行担当が範囲と現行仕様の整合を確認。

## PRと受け入れ

- 独立に受け入れと差し戻しができる短命ブランチと、目的が一つのレビュー付きPRで進めます。先行の3是正、同値整理、目に見える標準化、CIガードを同じPRに混ぜません。P7の二つの画面やP8の表示判断とガードは、必要なら独立PRに分けます。計画時点ではPRの個数や実装日数を固定せず、P1の再現・実装・回帰を終えた時点で残りの検証負担を見直します。
- 各UI変更では同じ合成データ、画面幅、テーマ、言語、操作状態で変更前後の基準SHAと原画像を記録し、対象のチケットに添付し、Acceptanceへの移動・完了の前に実際に表示できることを確認します。操作の挙動を直す場合は状態の系列と再読込・API等の保存結果を併記します。明暗・日英のPC標準幅を起点に、影響する狭幅、focus、hover、選択、disabled、通信中、失敗・取消を選びます。共通CSSによる行やタイトルの寸法変更も含め、仮想化・ドラッグへ影響する場合は、List・Group・Kanbanの該当する既存E2Eで表示件数・描画範囲、行高、スクロール・フォーカス復帰、移動後の保存を確認します。計時は性能に波及する変更で、同じデータを使って比較します。[UI/UXレビュー規則](https://github.com/wamukat/kanbalone/blob/2ff8489d889706a6dc6392fd28aeff073e0b515c/docs/development/ui-ux-review.md)
- 意図した可視差はその差と影響外の維持を、同値整理は対象のcomputed style・位置・操作結果の同等性を確認します。既存の `pnpm check`、関連Chromium E2E、独立の差分レビューとPRのRequired checksを通し、ユーザーがチャットで受け入れた差分と現在の差分の一致を確認してからマージします。受け入れ後に差分が変わった場合は変更点を示して受け入れを取り直します。リリースや通常環境への反映は別途認められた範囲で行います。
- ロールバックは原因のPRを対象に、通常のレビューと検証を通すrevertのPRで行います。後続PRが変更した共通元を利用している場合は、利用側を戻すか互換性を保つ修正を先に検証します。今回の予定にはDBマイグレーションを含めないため、CSS・マークアップ・検査の差分を戻して保存結果を確認します。誤検知で止まるガードは対象ガードだけを戻し、表示是正の受け入れを維持します。

## 終了条件

P9の照合で、固定した利用先が標準か明示された用途差を使い、同じ問題が再発したときに代表の検証で検知できれば、この計画を閉じます。未観測の4群、ナビ密度、他画面の新しい用途差は、必要な状態を再現したときに別の検討へ進めます。監査の全1,301行と原画像を毎回更新することは完了条件に含めません。
